# Feature: Scrape and Store Product Brand and Producer from Rimi.lv

I have an existing project that scrapes product information from Rimi.lv.

Add a new feature to scrape, normalize, deduplicate, store, and link **product brand** and **producer/manufacturer** information found on Rimi.lv product pages.

Do not break or change the existing scraping functionality.

Before making changes, inspect the existing project structure, database schema, ORM/database library, migrations, scraper architecture, models, and tests. Use the existing project's conventions rather than introducing a new framework or database technology.

---

## 1. Functional requirements

For each Rimi product page, look for these HTML labels:

```html
<span>Zīmols</span>
<span>Ražotājs</span>
```

The corresponding values should be extracted from the product page.

Example product:

[https://www.rimi.lv/e-veikals/lv/produkti/maize-un-konditoreja/konditoreja/kukas-un-kucinas/kucinas-skudrupuznisi-6x50g/p/275915](https://www.rimi.lv/e-veikals/lv/produkti/maize-un-konditoreja/konditoreja/kukas-un-kucinas/kucinas-skudrupuznisi-6x50g/p/275915)

The page contains:

```text
Zīmols: Staburadze
Ražotājs: Orkla Latvija SIA
```

The scraper should extract:

```text
brand = Staburadze
producer = Orkla Latvija SIA
```

The exact HTML structure around these labels should be inspected carefully. Do not assume that the value is always located in the same exact sibling element without verifying the real page structure.

# 2. Database design

Create two new main tables:

```text
brands
producers
```

Because a producer can own/manufacture several brands, also create a relationship table:

```text
brand_producers
```

The product itself should have at most:

```text
0..1 brand
0..1 producer
```

A product may have a brand without a producer, or a producer without a brand.

---

## 3. `brands` table

Create a `brands` table following the existing project's database conventions.

At minimum:

```text
id
name
normalized_name
website_url
created_at
updated_at
```

Where:

* `name` = canonical/display name, preserving a sensible human-readable version from Rimi
* `normalized_name` = normalized value used for matching/deduplication
* `website_url` = nullable; this will be filled manually later
* timestamps should follow existing project conventions

Add a unique constraint/index on:

```text
normalized_name
```

so duplicate brands cannot accidentally be created.

# 5. `brand_producers` relationship table

Create a many-to-many relationship:

```text
brand_producers
```

Suggested fields:

```text
id
brand_id
producer_id
created_at
```

Add a unique constraint on:

```text
(brand_id, producer_id)
```

This is important because the same brand/producer relationship must not be inserted repeatedly every time a product is scraped.

Example:

```text
Staburadze
    |
    +--- Orkla Latvija SIA
```

And later it should be possible to have:

```text
Orkla Latvija SIA
    |
    +--- Staburadze
    +--- Laima
    +--- Selga
```

# 6. Add relationships to products

Modify the existing products table/model to support:

```text
brand_id
producer_id
```

Both must be nullable.

Therefore:

```text
Product
  ├── brand_id → Brand (nullable)
  └── producer_id → Producer (nullable)
```

A product must never be forced to have either one.

Examples:

### Product with both

```text
Product A
brand: Staburadze
producer: Orkla Latvija SIA
```

### Product with only brand

```text
Product B
brand: Coca-Cola
producer: NULL
```

### Product with only producer

```text
Product C
brand: NULL
producer: Some Producer SIA
```

### Product with neither

```text
Product D
brand: NULL
producer: NULL
```

Do not create placeholder records such as `"Unknown"` or `"N/A"`.

# 7. Normalization and deduplication

This is an important part of the feature.

The scraper must not create separate records for differences such as:

```text
Staburadze
STABURADZE
staburadze
 Staburadze
Staburadze 
```

These must resolve to the same brand.

Likewise:

```text
Orkla Latvija SIA
ORKLA LATVIJA SIA
Orkla Latvija SIA 
```

must resolve to the same producer.

Create a reusable normalization function/service.

At minimum normalization should:

1. Trim leading/trailing whitespace.
2. Collapse repeated whitespace.
3. Normalize Unicode consistently.
4. Perform case-insensitive matching.
5. Preserve Latvian characters correctly.
6. Use the normalized value only for matching/deduplication.
7. Preserve a human-readable canonical `name` separately.

For example:

```text
original:
"  STABURADZE  "

normalized:
"staburadze"
```

Do not remove Latvian diacritics merely to perform normalization. For example, `Ražotājs` is not equivalent to arbitrarily stripping `ž`.

Use Unicode-aware normalization.

# 8. Handling canonical names

When a new brand/producer is encountered:

1. Calculate `normalized_name`.
2. Search for an existing record using `normalized_name`.
3. If found, reuse that record.
4. If not found, create a new record.
5. Never create a duplicate solely because capitalization or whitespace differs.

For an existing record, do not blindly overwrite its canonical `name` on every scrape.

This is important because the canonical name may later be manually corrected.

The same applies to:

```text
website_url
```

The scraper must NEVER overwrite a manually entered website URL.

# 9. Product scraping workflow

Update the existing product scraping process.

After loading the Rimi product page:

1. Extract existing product information exactly as before.
2. Search for the `Zīmols` label.
3. Extract the corresponding brand value.
4. Search for the `Ražotājs` label.
5. Extract the corresponding producer value.
6. Normalize the extracted values.
7. Find or create the corresponding brand record.
8. Find or create the corresponding producer record.
9. Set the product's `brand_id` and/or `producer_id`.
10. If both brand and producer are present, create the `brand_producers` relationship.
11. Save the product.

Do not fail the entire product scrape if one or both fields are absent.

```text

```

```text

```

do not create another relationship row.

```text

```

If it has only:

```text
Producer: Orkla Latvija SIA
```

store the producer but do not create a brand-producer relationship.

# 11. What happens if product information changes?

The scraper must update the product's current brand/producer relationship.

For example, if an existing product previously had:

```text
brand = Staburadze
producer = Orkla Latvija SIA
```

and a later Rimi scrape says:

```text
brand = Staburadze
producer = Another Producer SIA
```

update the product's `producer_id`.

Do NOT delete the old producer or brand from the master tables.

Do NOT delete the old `brand_producers` relationship automatically unless it is certain that the relationship is no longer valid.

The relationship table represents known associations between brands and producers, not just the current state of one product.

# 12. Backfill existing products

This feature must include a backfill process.

Existing products in the database currently do not have brand/producer information.

Create a backfill process that:

1. Gets existing products from the database.
2. Uses their existing Rimi product URL.
3. Re-fetches the Rimi product page.
4. Extracts brand and producer.
5. Normalizes the values.
6. Finds/creates brand and producer records.
7. Updates the product.
8. Creates the brand-producer relationship where applicable.
9. Continues if an individual product fails.

Do not stop the entire backfill because one Rimi page fails.

Log failures clearly.

The backfill should be safe to run multiple times.

Running it twice must not create duplicate:

* brands
* producers
* brand_producers relationships

# 22. Important architectural requirement

Keep **brand** and **producer** as independent master entities.

Do NOT store brand and producer only as text columns on products.

The intended architecture is:

```text
                    ┌───────────┐
                    │  brands   │
                    └─────┬─────┘
                          │
                          │
                  ┌───────▼────────┐
                  │ brand_producers│
                  └───────┬────────┘
                          │
                          │
                    ┌─────▼──────┐
                    │ producers  │
                    └────────────┘


products
   │
   ├── brand_id ────────→ brands
   │
   └── producer_id ─────→ producers
```

This is important because:

* one producer can have multiple brands
* one brand can be associated with multiple producers
* products can use only a brand
* products can use only a producer
* website information belongs to the brand/producer entity, not the individual product

---

# 23. Do not overwrite manually enriched data

The scraper is responsible for:

* discovering brand/producer names
* creating entities
* linking products
* creating brand-producer associations

The scraper is NOT responsible for:

* finding websites
* changing manually entered website URLs
* deleting brands/producers
* replacing manually curated canonical information without a clear reason

Treat `website_url` as manually managed data.
